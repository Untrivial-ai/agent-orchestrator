Phase C — durable scheduled automations

Detailed implementation plan for recurring unattended AO sessions in the Go rewrite.
Derived from plan-git-state-automations-port-detection.html and the approved engineering specification at docs/superpowers/specs/2026-08-25-phase-c-automations-design.md · target branch feat/phase-c-automations
What this implementation ships — one complete vertical slice for defining, scheduling, spawning, recovering, and inspecting recurring AO work:
  1. Durable automation definitions and per-occurrence run history in SQLite.
  2. Validated RRULE scheduling with explicit IANA timezone support and five-field cron input sugar.
  3. Daemon-owned materialization, transactional claims, non-overlapping dispatch, and bounded crash recovery.
  4. Idempotent creation of ordinary AO sessions through the existing session service.
  5. REST CRUD + run history, thin ao automation CLI commands, and an Electron Automations screen.
  6. Generated API/sqlc artifacts, narrow tests throughout, broad automated verification, and manual desktop proof before the PR ships.
Decisions already resolved:
  • Delivery guarantee is at least once; application idempotency prevents duplicate sessions in normal retries.
  • One automation may have only one spawning or running occurrence. Later due occurrences remain pending.
  • Restart catch-up is capped at three missed occurrences; next_run_at always advances beyond the current time.
  • Disabling pauses new materialization and dispatch. It does not kill a running session, delete history, or replay the disabled interval when re-enabled.
  • A run completes only when the linked session is durably is_terminated. An unavailable runtime probe is not proof of death.
  • The daemon remains the authority. The frontend and CLI do not open SQLite or spawn agents directly.

1. Architecture Daemon-owned

Goal: add scheduling as a daemon service without creating a second agent execution path or moving durable behavior into Electron.

Existing patterns to reuse

  • Background observer: follow observe/reaper and observe/trackerintake for ticker ownership, context cancellation, logging, and shutdown channel behavior.
  • Daemon wiring: construct the automation service after storage and session services exist; reconcile before beginning the recurring observer.
  • Spawn boundary: extend the current service-level spawn configuration rather than importing a controller or recreating worktree/runtime logic.
  • Error shape: reuse apierr and the current request-ID/error envelope path.
  • Generated contracts: edit controller DTO/spec sources, then regenerate; never hand-maintain generated OpenAPI or sqlc code.

2. Domain model New vocabulary

Goal: make persisted facts and state transitions explicit without storing derived UI status.

Core types

    AutomationKindWorker       AutomationKind = "worker"

)

type AutomationRunStatus string
const (
    RunPending   AutomationRunStatus = "pending"
    RunSpawning  AutomationRunStatus = "spawning"
    RunRunning   AutomationRunStatus = "running"
    RunCompleted AutomationRunStatus = "completed"
    RunFailed    AutomationRunStatus = "failed"
)
Validation invariants
  • display_name: trimmed, 1–120 characters.
  • prompt: trimmed, 1–4096 characters; never copied into run errors or routine logs.
  • kind: only worker or orchestrator.
  • harness: optional; empty resolves through AO’s existing configured default.
  • timezone: required valid IANA name; timestamps persist in UTC.
  • Exactly one schedule input on create: rrule or cron.

3. Persistence Migration 0109

Goal: persist definitions, occurrence identities, claims, spawn links, and terminal outcomes strongly enough to recover after any daemon interruption.

CDC and deletion behavior

  • Do not widen the mature change_log.event_type allowlist for this feature; automation mutations use direct query-cache updates plus a short visible-page refetch interval.
  • Do not emit parallel manual CDC events from store methods. Existing session CDC refreshes linked-session presentation.
  • Deleting an automation cascades run history. Spawned sessions remain durable user work.
  • Disabling changes only future scheduler behavior. Existing history and a currently running session remain untouched.

4. Schedule parsing and validation Timezone-safe

Goal: canonicalize every accepted schedule into an RRULE plus IANA timezone and compute deterministic future occurrences.
Create / update pipeline
  1. Trim input and require exactly one of rrule or cron.
  2. Load the supplied IANA timezone. Reject ambiguous fixed abbreviations such as IST.
  3. For cron, accept standard five-field syntax and translate only when meaning is preserved; reject unsupported constructs.
  4. Parse the canonical RRULE and reject unsupported forms, rules with no future occurrence, and frequency faster than one minute.
  5. Calculate next_run_at using the named zone, then persist UTC. Retain the RRULE and timezone for future advancement.
DST contract

Wall-clock intent belongs to the named timezone; storage and comparisons use UTC. Tests lock behavior for spring-forward gaps, fall-back repeated hours, monthly boundaries, leap days, and month-end schedules. The recurrence library stays behind the service boundary.

5. Materialization and dispatch At least once

Goal: turn due times into durable runs before spawning, prevent overlap, and guarantee progress even when spawning fails.

Tick algorithm

  1. The observer calls automation.Service.Tick(ctx, now.UTC()); it contains no scheduling logic.
  2. For each enabled due definition, open a transaction and enumerate occurrences from persisted next_run_at.
  3. Insert at most three pending rows; the unique occurrence key makes repeated polls harmless.
  4. Set last_run_at to the last materialized occurrence and advance next_run_at strictly beyond now, even when more than three were missed.
  5. After commit, select the oldest eligible pending run for each automation.
  6. If a sibling is spawning or running, leave the pending occurrence queued.
  7. Acquire a bounded lease and increment attempt_count transactionally.
  8. Spawn through the existing session service; attach the session and mark the run running.
pending --claim lease--> spawning --session linked--> running --session terminated--> completed
   |                         |
   | waits behind active     +-- permanent structural failure --------------------> failed
   | run                     +-- crash or transient interruption -----------------> reconcile

6. Startup reconciliation Crash recovery

Goal: repair interrupted state before the recurring observer creates new work.
Daemon startup order
  1. Open storage and construct current runtime/session services.
  2. Construct automation store/service dependencies.
  3. Run automationService.Reconcile(ctx) best-effort with structured logs.
  4. Start the automation observer after reconciliation returns.
  5. On shutdown, cancel the shared context and wait for its completion channel.
Persisted stateRecovery action
Expired spawning lease with linked sessionRead durable session facts; mark running or completed.
Expired lease without link, but session found by automation_run_idAttach it; do not spawn a duplicate.
Expired lease and no matching sessionReturn to eligible retry while preserving attempt history.
running with terminated linked sessionMark completed and set finished_at.
running with missing/non-terminated sessionRemain running unless durable structure proves permanent invalidity.
Definition due during downtimeMaterialize up to three missed occurrences and advance beyond now.

7. Session integration Existing spawn path

Goal: make an automated run a normal AO session after creation while retaining its origin link.
  • Add optional AutomationRunID to the service/port spawn configuration and persist it with session creation.
  • Before spawning, query by run ID. If a session exists, return/link it as the idempotent result.
  • If two workers race, the unique link selects a winner; the loser re-reads the winning session.
  • Populate project, prompt, kind, and optional harness from the definition. Resolve remaining defaults through the existing spawn flow.
  • Do not add automation-specific worktree, terminal, agent, reaper, or display-status logic.
  • Use durable is_terminated as completion proof. Failed/unknown probes do not complete a run.

  • Use existing commandContext JSON helpers and mirrored CLI DTO patterns.
  • Return usageError for invalid/missing arguments so misuse exits 2.
  • Preserve daemon error envelopes for service failures so they exit 1 with actionable context.
  • Require destructive confirmation for delete unless --yes is passed.
  • Default output is concise human-readable tables; --json exposes stable structures.

10. Electron frontend Supervisor UI

Goal: make automations discoverable and operable without moving scheduler logic into React.

Global Automations screen

  • Add Automations to global navigation rather than nesting it inside one session.
  • Rows show name, project, humanized schedule + timezone, next run, latest status, and enabled state.
  • Create/edit dialog provides daily/weekly presets plus advanced raw RRULE or cron input; the server remains authoritative.
  • Enabled toggle is optimistic but rolls back and shows the daemon error when mutation fails.
  • Delete confirmation explains that history is removed while spawned sessions remain.
  • Expandable run history shows schedule time, status, attempts, failure context, and a link to the spawned session.
Query behavior

Add list/detail/run hooks and mutations around the generated API client. Update or invalidate exact query keys after writes. Do not invent manual CDC event types in this PR; use direct cache updates plus a short refetch interval while visible. Existing session CDC updates linked-session presentation.

12. Implementation sequence One PR

Goal: keep commits reviewable while building one coherent vertical feature.
Step 1 — Domain and persistence foundation

Write schema/store tests; add domain types, migration, queries, session link, and regenerate sqlc. Verify up/down, constraints, and query ordering.

Step 2 — Recurrence engine core

Add the recurrence dependency behind a narrow service wrapper. Drive RRULE, cron, timezone, DST, validation, and next-occurrence behavior through table tests.

Step 3 — Scheduler and recovery reliability

Implement materialization, non-overlap, claims, idempotent spawn linking, completion, and startup catch-up using injected clocks and fakes.

Step 4 — REST and generated API contract

Add routes/DTOs/errors, regenerate API artifacts, and run route/spec parity tests.

Step 5 — CLI and Electron surfaces

Add thin CLI parity and the global typed frontend view. Cover validation, rollback, delete, history, and session navigation.

Step 6 — Integration hardening ship gate

Run focused then broad verification. Exercise daemon restarts and real schedules in Electron, document intentional omissions, and open one Phase C PR.

14. Manual verification AO desktop

Goal: prove the real Electron supervisor, daemon, session lifecycle, and restart behavior—not only isolated services.
  • Create: create a near-future one-minute automation and verify schedule, timezone, and next run.
  • Dispatch: confirm exactly one normal AO session appears with expected project, prompt, kind, and harness.
  • History: confirm pending → spawning → running and the session link.
  • Completion: terminate through normal AO controls and confirm the run becomes completed.
  • Non-overlap: keep one session running through the next occurrence; confirm the later run waits pending.
  • Restart before spawn: restart after claim; confirm recovery creates or links exactly one session.
  • Restart after spawn: restart before run linking; confirm the existing session is attached.
  • Catch-up: simulate more than three missed occurrences; confirm only three materialize and next run is future.
  • Disable/re-enable: confirm no new work while disabled and no disabled-window replay.
  • Error: provoke a permanent dependency failure; confirm useful bounded context without prompt leakage.
  • Delete: confirm definition/history disappear while the spawned session remains usable.
  • CLI parity: exercise create/list/get/update/runs/delete and observe the same state in Electron.

15. Definition of done PR ready

  • All new state remains beneath the existing ~/.ao data directory.
  • The primary listener remains loopback-only; no new network-facing bind is added.
  • The CLI remains an HTTP client and Electron remains a supervisor.
  • No merged migration or generated sqlc file is hand-edited.
  • OpenAPI and frontend schema artifacts are regenerated and committed together.
  • Duplicate polls/restarts cannot duplicate occurrence rows or linked sessions in the covered failure model.
  • Unknown runtime health never terminates or completes work.
  • Catch-up, non-overlap, disable, re-enable, and delete semantics match this plan.
  • Narrow tests, race/build/vet, lint, frontend typecheck/build, and manual Electron scenarios pass.
  • The PR body explains intentional omissions and any investigation documented instead of changed.
Intentional omissions
  • No seconds-level schedules, event/webhook triggers, or distributed multi-daemon scheduling.
  • No overlapping runs or configurable catch-up policy beyond the fixed cap.
  • No force-kill when an automation is disabled or deleted.
  • No manual “run now” unless it falls out naturally without weakening occurrence identity.
  • No new custom CDC protocol solely for the Automations screen.
