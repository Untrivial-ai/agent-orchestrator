# tmux and systemd worker lifecycle research

Version: v1.0

Date: 2026-08-11

Status: current for PR #3550 design

Evidence cutoff: 2026-08-11

## Purpose

This record answers the compatibility questions exposed while reviewing
[upstream PR #3550](https://github.com/Untrivial-ai/agent-orchestrator/pull/3550):

1. whether a canceled or timed-out tmux client proves that `new-session` did
   not take effect;
2. how AO can distinguish one worker launch from another without deleting a
   concurrent creator's runtime;
3. when a worktree may be rolled back after runtime creation or teardown
   fails; and
4. which guarantees belong in the bounded containment hardening slice (C)
   versus the durable lifecycle and rollout slice (D).

This is a compatibility record, not final acceptance evidence for a future PR
head. Every canary and hosted check must be rerun on the exact implementation
head.

## Executive conclusion

The source repository already assumes that `Runtime.Create` returning an error
means spawn may remove the worktree. It also has tmux paths that discard
cleanup errors. PR #3550 did not introduce those caller behaviors, but adding a
second externally managed resource (a systemd scope) makes the latent contract
gap more consequential.

The bounded fix is not a general lifecycle redesign. It needs three properties:

- one launch identity, the existing `RuntimeLaunchID`, carried through the
  internal runtime port, tmux metadata, and systemd unit identity;
- explicit distinction between rollback-safe failures and outcomes that require
  preserving the session row and worktree; and
- exact-generation cleanup that never kills a tmux session or scope merely
  because its session-level name matches.

Unknown ownership must choose a possible leak over deleting another launch.
Durable retry, daemon-crash reconciliation, default enablement, resource limits,
and cleanup-state persistence remain D.

## tmux observations

### Client and server are separate processes

tmux sessions are owned by a server, while CLI invocations are clients that
communicate with that server over a socket. The tmux 3.2 manual describes this
separation and states that sessions survive client disconnection
([tmux 3.2 manual](https://github.com/tmux/tmux/blob/3.2/tmux.1)).

Go's `exec.CommandContext` cancels by killing the command process by default
([Go `os/exec`](https://pkg.go.dev/os/exec#CommandContext)). Applied to a tmux
CLI, that proves only that the client stopped. If the client had already sent
the command, it does not prove that the tmux server rejected or rolled it back.
This combined conclusion is an inference from the two documented boundaries;
it is why cancellation and timeout are uncertain outcomes.

### Command sequences provide ordered ownership marking, not a transaction

tmux 3.2 executes parsed commands in a per-client queue. Commands separated by
semicolons form a sequence, and an error prevents later commands in that
sequence from running
([tmux 3.2 command parsing](https://github.com/tmux/tmux/blob/3.2/tmux.1#L397-L520)).
tmux user options are string metadata with names prefixed by `@`; they can be
stored at session scope
([tmux advanced use](https://github.com/tmux/tmux/wiki/Advanced-Use#user-options)).

This supports the sequence:

```text
new-session ... ; set-option -t <session> @ao-runtime-launch-id <launch-id>
```

If `new-session` loses a duplicate-name race, the marker write does not run.
The sequence is nevertheless not treated as an ACID transaction: cancellation,
socket failure, or an ownership-probe failure can still leave AO unable to prove
which commands completed. A missing or unreadable marker therefore means
"preserve", not "safe to delete".

The marker is also not a security boundary. Any process able to use the same
tmux server can mutate it. It is cooperative instance identity for AO's
single-user runtime, backed by exact systemd unit identity and conservative
cleanup decisions.

### Isolated duplicate-creator experiment

An isolated tmux server was run on 2026-08-11 using host tmux 3.7b. The winner
created session `sess` and set `@ao-runtime-launch-id=winner` in one command
sequence. A second sequence attempted the same session name with value `loser`.

Observed result:

```text
duplicate exit code: 1
duplicate output: duplicate session: sess
final option value: winner
```

The experiment used a dedicated `TMUX_TMPDIR`, shut down its server, and left no
AO runtime, service, database, or production state. It confirms the
duplicate-error property on the observed version. The implementation must still
retain tests compatible with the repository minimum tmux 3.2.

## systemd observations

`systemd-run --scope` creates a transient scope while the command remains a
child of `systemd-run`; systemd manages the command's processes in the scope
([`systemd-run(1)`](https://man7.org/linux/man-pages/man1/systemd-run.1.html)).
`KillMode=control-group` terminates every remaining process in the unit's
control group, and `SendSIGKILL=yes` permits escalation after the stop timeout
([`systemd.kill(5)`](https://man7.org/linux/man-pages/man5/systemd.kill.5.html)).

This cgroup ownership is why a descendant that calls `setsid` remains
contained: POSIX session identity changes, but cgroup membership does not
automatically change.

A systemd scope is a second external resource with its own state and failure
surface. `systemctl stop` returning an error or a final-state probe failing does
not prove the scope is empty. A session-only deterministic unit name also
cannot distinguish an old launch from a replacement launch. C therefore needs
a unit identity derived from both session identity and `RuntimeLaunchID`, and a
nil teardown result only after the exact unit is inactive/dead or not found.

## Patterns from mature runtimes and controllers

These projects are architectural comparisons, not dependencies AO will import.

### Kubernetes: preserve the owner record until cleanup completes

Kubernetes finalizers keep an object present, marked for deletion, while a
controller cleans owned resources. Only after the cleanup condition is met is
the finalizer removed and object deletion completed
([Kubernetes finalizers](https://kubernetes.io/docs/concepts/overview/working-with-objects/finalizers/)).
Delete preconditions can name the exact target UID and resource version
([Kubernetes preconditions](https://kubernetes.io/docs/reference/kubernetes-api/definitions/preconditions-v1-meta/)).

The transferable principles are:

- keep the durable owner while external cleanup is unconfirmed; and
- target one generation, not merely a reusable logical name.

C applies these principles through current call outcomes and existing session
metadata. It does not persist cleanup intent, retry ownership, or a
restart-time reconciliation obligation; those belong to D.

### containerd: stable task identity and an explicit lost-connection delete path

containerd Runtime v2 creates tasks under an explicit task ID and specifies a
separate delete command for resources left when containerd cannot communicate
with a shim or reconnects after boot
([Runtime v2 delete contract](https://github.com/containerd/containerd/blob/main/docs/runtime-v2.md#delete)).
Its lifecycle flow separates create, start, exit, and delete events
([Runtime v2 flow](https://github.com/containerd/containerd/blob/main/docs/runtime-v2.md#flow)).

The useful lesson is not to copy containerd's protocol. It is that losing the
success response does not erase resource identity or the need for a later,
explicit cleanup operation.

### Nomad: instance IDs and cleanup before allocation garbage collection

Nomad gives each allocation a full allocation ID and exposes it to tasks
([runtime environment](https://developer.hashicorp.com/nomad/docs/reference/runtime-environment-settings)).
Its client garbage collection asks the task driver to clean task resources
before reclaiming an allocation
([Nomad garbage collection](https://developer.hashicorp.com/nomad/docs/manage/garbage-collection)).

The applicable pattern is again an instance-scoped lifecycle. A logical job or
session name is not enough to identify one concrete launch.

## AO-specific findings

### Shared runtime wiring currently exceeds the stated worker-only contract

At PR head `59a317a2`, daemon configuration constructs one runtime adapter with
the global containment option. Session workers, reviewers, and standalone shell
terminals share that adapter. The tmux implementation selects containment from
adapter state rather than per-launch worker identity.

Consequences if left unchanged include:

- reviewer and shell-terminal `Create` calls entering systemd containment even
  though PR #3550 describes worker processes only; and
- their `Destroy` calls skipping the legacy SID reaper whenever the shared
  adapter has containment enabled.

C must make containment per managed-agent launch. Worker and orchestrator TUI
controllers carry a non-empty `RuntimeLaunchID`; reviewer and shell-terminal
calls do not and must retain legacy behavior.

### Relationship to issue #3807

[#3807](https://github.com/Untrivial-ai/agent-orchestrator/issues/3807) is a
separate worktree-filesystem defect: owner-owned read-only directories can make
worktree removal fail. It composes with this lifecycle boundary because cleanup
must first confirm runtime release and then remove the workspace safely.

C does not fix filesystem permissions. It prevents AO from attempting worktree
removal while runtime ownership is unresolved. A later removal can still hit
#3807 and must preserve the row/worktree according to the existing workspace
failure path. Durable retry coordination belongs in D after the independent
#3807 fix exists.

## Decision impact

The evidence supports the following bounded design:

1. Replace the separate random creation token with the already generated
   `RuntimeLaunchID`.
2. Carry that ID explicitly in the internal runtime config and handle.
3. Derive tmux ownership metadata and the systemd unit name from the same ID.
4. Make failed Create outcomes say whether workspace rollback is safe.
5. Preserve the session row and worktree whenever ownership or cleanup is
   foreign, unknown, or unconfirmed.
6. Stop an old exact generation before starting its replacement.
7. Freeze C after exact-head verification; move crash recovery, persistence,
   resource policy, and default rollout to D.

Review this record again if AO changes its minimum tmux version, replaces
systemd scopes, gives reviewers/shell terminals durable launch IDs, or adopts a
persisted cleanup-state model.
