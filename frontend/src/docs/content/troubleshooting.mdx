## Start with the desktop app

The desktop app owns the local daemon. First quit and reopen Agent Orchestrator, then confirm the project and selected session still appear. The app discovers or restarts its daemon and reconnects live event and terminal streams.

If you use the optional CLI, `ao status` and `ao doctor` provide additional local diagnostics:

```bash
ao status
ao doctor
ao doctor --json
```

`ao doctor` checks daemon/config state, the data directory and database, Git, and tmux on macOS/Linux. It is not required for a normal desktop-only install.

## Desktop and daemon

<Accordions>
	<Accordion title="The app opens but no projects appear">
		Confirm you opened the expected AO data home. All state defaults under `~/.ao`; an `AO_DATA_DIR` or `AO_RUN_FILE` override can point a development launch at a different daemon instance.
	</Accordion>
	<Accordion title="The CLI says the daemon is not running">
		Open the desktop app first. Product CLI commands are thin clients and need the app-owned daemon. A stale `~/.ao/running.json` is not enough; AO also verifies the recorded process.
	</Accordion>
	<Accordion title="The daemon port is occupied">
		The primary daemon uses loopback port `3001` by default and fails fast if it cannot bind. Stop the conflicting local process or use a deliberate development `AO_PORT` override. Never change the bind host to expose the daemon.
	</Accordion>
	<Accordion title="The UI looks stale after a daemon restart">
		Leave the app open briefly so its SSE connection can reconnect and invalidate current queries. If it does not recover, restart the desktop app. The event stream supports replay, but a full app restart is the safest user-level recovery.
	</Accordion>
</Accordions>

## Agents and sessions

<Accordions>
	<Accordion title="No agent harness is offered">
		Install the harness, run it once to authenticate, and restart AO. The desktop daemon inherits a login-shell environment and reuses each provider's installed binary and authentication.
	</Accordion>
	<Accordion title="Chat preflight fails">
		Confirm the selected harness supports native Chat and its binary is authenticated. Chat support depends on the harness and installed version; see the [agent capability catalog](/plugins/agents#chat-versus-terminal-ui). Check **Settings → Harnesses** and provider version/permission requirements. Choose Terminal UI when the harness lacks Chat support or preflight cannot connect.
	</Accordion>
	<Accordion title="A TUI session will not start on macOS or Linux">
		New macOS/Linux sessions use detached native PTY hosts. Packaged builds bundle tmux for old sessions/fallback; macOS still validates it. For source runs check configured/system tmux and the native-host launch error. Windows uses ConPTY. See [Runtime](/plugins/runtimes).
	</Accordion>
	<Accordion title="The session is blocked">
		Open the session and answer the pending approval or permission prompt. AO deliberately does not inject lifecycle messages while a controller is blocked.
	</Accordion>
	<Accordion title="The status appears wrong">
		Status is derived from activity, termination, controller, and pull-request facts. A failed runtime probe is not treated as death. Reopen the session and inspect its Chat or terminal before killing it.
	</Accordion>
	<Accordion title="A session will not restore">
		Use the desktop restore action or `ao session restore <session-id>`. Restore reuses the same session and worktree when the selected adapter supports recovery. Check that the harness remains installed and authenticated. For a stopped controller on a non-terminated session use `ao session resume-agent <id>` instead. A disabled interface switch can indicate unavailable native history, an unsupported direction, or pending recovery; inspect its reason before retrying.
	</Accordion>
</Accordions>

## GitHub and pull requests

<Accordions>
	<Accordion title="Repository or pull-request data is missing">
		Run `gh auth status` and confirm the active account can access the repository. GitHub authentication is lazy so an auth failure does not need to block unrelated local session work. For GitLab check token/`glab` authentication and self-managed-host configuration in [SCM setup](/plugins/scm).
	</Accordion>
	<Accordion title="The agent opened a PR but AO did not link it">
		Claim it from the session UI or, inside the worker, run `ao session claim-pr <pr-number-or-url>`; AO reads the worker from `AO_SESSION_ID`. From another shell, use `ao session claim-pr <session-id> <pr-number-or-url>`.
	</Accordion>
	<Accordion title="CI or review data is delayed">
		The SCM observer polls GitHub and respects rate limits and ETags. Check `gh auth status`, wait for another observation cycle, and open the pull request directly for full raw logs or comment bodies.
	</Accordion>
	<Accordion title="Review findings were not sent to the worker">
		Open the review run and use its send action. Reviewer execution and delivery are separate operations so you can inspect findings before changing the worker conversation.
	</Accordion>
</Accordions>

## Browser preview

<Accordions>
	<Accordion title="The Browser tab is blank">
		Select a target explicitly with `ao preview <url>`, or use `ao preview start` when the worktree contains a valid `.ao/launch.json`. AO does not auto-discover a preview for every new worker.
	</Accordion>
	<Accordion title="A configured preview server will not start">
		Run `ao preview start <configuration>` and inspect the returned error. Verify the command and working directory in the session's `.ao/launch.json`, then run the same command in its worktree shell.
	</Accordion>
	<Accordion title="Browser automation targets the wrong page">
		Select the correct session and browser tab. Commands are authorized for the selected session. Temporary profiles are isolated; named profiles deliberately reuse saved browser state. Check the selected profile, and refresh snapshots after navigation. Keep the panel visible for screenshots/human pointer actions. Profile imports have platform-dependent cookie support; a missing login may require signing in again.
	</Accordion>
</Accordions>

## Connect Mobile

<Accordions>
	<Accordion title="The phone cannot connect">
		Confirm Connect Mobile is enabled and the QR is ready, then use the latest offer/password. Direct LAN needs the same trusted network; remote access needs an advertised, ready secure endpoint. Inspect connector/Tailscale setup failures, and update both apps for identity/contract mismatches. Rotating the password invalidates old credentials.
	</Accordion>
	<Accordion title="The QR code was shared">
		The current QR carries the host identity, available endpoints, and connection password in a v2 pairing link. Treat it as a bearer credential: do not share the QR or screenshots of it. Rotate the connection password in desktop settings if it may have been exposed.
	</Accordion>
	<Accordion title="Can I use Connect Mobile on public Wi-Fi?">
		Do not use a plaintext LAN endpoint on an untrusted network. Use an available secure endpoint from [Connect Mobile](/configuration/remote-access). Keep the primary daemon private. If mobile push is missing, check phone notification permission, device mute state, and daemon connectivity.
	</Accordion>
</Accordions>

## Still stuck

| Symptom | Where to go |
| --- | --- |
| macOS Gatekeeper says the developer cannot be verified | Follow the Gatekeeper steps in [Common Installation Problems](/installation#common-installation-problems). |

Open an issue in the [Agent Orchestrator repository](https://github.com/Untrivial-ai/agent-orchestrator/issues). Include the desktop version, operating system, agent harness and interface mode, reproduction steps, and sanitized `ao doctor --json` output when the CLI is available. Never attach credentials, provider transcripts, or the entire `~/.ao` directory.
