---
title: Per-role agents
description: Configure separate harnesses and models for worker and orchestrator sessions.
---

AO has two session roles:

- A **worker** implements a focused task in an isolated workspace and may own pull requests.
- An **orchestrator** supervises a project, monitors sessions, and delegates implementation to workers.

Role and interface are separate choices. Either role can start in structured Chat or Terminal UI when its harness supports that interface.

## Configure roles

Open Project Settings in the desktop app and choose a coding agent for each role. The CLI can set these agents while registering a project:

```bash
ao project add --path /absolute/path/to/repo \
  --worker-agent codex \
  --orchestrator-agent claude-code
```

For a full configuration replacement, the stored JSON shape is:

```json
{
  "worker": {
    "agent": "codex",
    "agentConfig": {
      "model": "gpt-5.4",
      "permissions": "bypass-permissions"
    }
  },
  "orchestrator": {
    "agent": "claude-code",
    "agentConfig": {
      "model": "claude-opus-4"
    }
  }
}
```

This example uses `bypass-permissions`, which lets provider tools act without their normal approval prompts. Use it only when intended; available permission modes depend on the provider.

The `--config-json` flag takes a JSON string, not a file, and `set-config` replaces the whole project configuration. Preserve existing setup, rules, reviewers, and intake settings. See [Projects: update from the CLI](/configuration/projects#update-from-the-cli) for CLI limitations and safer alternatives.

## Start an orchestrator or worker

The desktop provides dedicated new-session and orchestrator flows. From the CLI:

```bash
ao spawn --project my-project --kind orchestrator \
  --name supervisor --mode chat

ao spawn --project my-project --kind worker \
  --name issue-42 --issue 42 --mode tui
```

`--name` is required and limited to 100 characters. Use `--harness` to choose a different agent for one spawn.

## Choose Chat or Terminal UI

- Use **Chat** for structured messages, provider activity, approvals, plans, changed files, usage, compaction, and rollback. Chat support depends on the harness and installed version; see the [agent capability catalog](/plugins/agents#chat-versus-terminal-ui).
- Use **Terminal UI** when you want the agent's native interface or a harness without native Chat support.

Compatible Claude Code and Codex sessions expose **Switch to chat UI** or **Switch to terminal UI**. Idle sessions switch directly. When work is active, AO asks whether to finish and drain it or stop and interrupt it before switching controllers.

The default interface comes from **Settings → General**. Project `agentConfig.mode` does not set Chat or Terminal UI. A choice made for a task or with the CLI takes precedence.

Model, reasoning effort, permissions, and provider execution modes depend on the selected agent. Chat support and the ability to switch interfaces are separate capabilities, so use the switch action offered for that session.

## Project rules

Use `agentRules` and `agentRulesFile` for worker instructions. Use `orchestratorRules` for supervision-specific guidance. These are stored in the typed project config and injected into the appropriate session role.

<Callout type="info">
	AO uses the provider CLI already installed and authenticated on your machine. Run `ao doctor` if a configured harness fails preflight.
</Callout>
