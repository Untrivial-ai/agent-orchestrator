---
title: OpenCode
description: Built-in Terminal UI and native ACP Chat support for the user's OpenCode installation.
---

AO resolves your local `opencode` executable and reuses its authentication.

```bash
ao agent ls --refresh
ao spawn --project my-app --name opencode-task --agent opencode --mode chat
```

OpenCode can run as its native Terminal UI or through its native ACP interface in structured Chat. Chat history is persisted by AO as a durable, paged conversation projection while provider conversation identity is retained for continuity.

AO offers the same approval choices in both surfaces. **Default approvals** leaves your OpenCode configuration untouched. **Accept edits** lets file changes run while shell commands, network access, and subagents ask. **Auto-approve** runs those too, including the out-of-worktree and repeat-loop guards OpenCode asks about by default. **Bypass permissions** allows every tool. `read` is never overridden, so OpenCode's default deny on `.env` files survives every mode except Bypass.

These grants outrank `deny` rules in your global or user configuration, so a mode that allows a tool allows it. A policy committed to the session worktree is treated differently — see below.

A repository policy always wins over AO. In the Terminal UI, AO writes its rules to a config file referenced by `OPENCODE_CONFIG`, which OpenCode loads before a worktree `opencode.json`. In Chat, AO injects one agent per mode into the inline runtime layer, so it applies that worktree policy over its own rules key by key — Accept edits and Auto grant only what the repository has not ruled on, and contribute nothing at all when the repository states a blanket policy or one AO cannot parse. Bypass permissions is the exception on both surfaces: it is OpenCode's own full-access setting.

The Chat picker switches between those agents, so OpenCode enforces the selected mode and a change applies immediately in either direction, including back to a stricter mode.

OpenCode is also a shipped reviewer harness. Reviewer configuration is independent from the worker harness; inspect project settings and `ao review --help` for the current review workflow.
